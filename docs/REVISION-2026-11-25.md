### T2 · P0 — La página 404 enlaza a URLs que no existen

**Fichero:** `src/pages/404.astro`

**Actual:**

```astro
<Base lang="es" title={t('notfound.title')} description={t('notfound.text')} path="404/" noindex>
```

`Base.astro` deriva de `path` el canonical, los `hreflang` y el selector de idioma del pie. Resultado
generado hoy en `dist/404.html`:

- `canonical` = `https://emili.godes.org/es/404/`
- `hreflang` y selector de idioma = `/ca/404/`, `/en/404/`… → **todos dan 404**

**Cambio.** Importar `pageAlternates` y pasar alternates reales a la portada de cada idioma:

```astro
import { pageAlternates } from '../lib/site';
…
<Base lang="es" title={t('notfound.title')} description={t('notfound.text')} path="404/" noindex
  alternates={pageAlternates('home')}>
```

`pageAlternates('home')` devuelve `{ es: '', ca: '', … }`, así que los `hreflang` pasan a apuntar a
`https://emili.godes.org/<lang>/` y x-default a `/es/`. El canonical puede seguir siendo `/es/404/`
(la página es `noindex`).

**Aceptación.** En `dist/404.html`: ningún enlace de navegación (selector de idioma del pie, `hreflang`,
x-default) contiene `/404/`; el `canonical` sigue siendo `https://emili.godes.org/es/404/` (la página es
`noindex`); el bloque `ul.eg-langlist` sigue listando los 6 idiomas y apunta a sus portadas.

### T3 · P1 — Slugs de proyecto desmesurados (hasta 234 caracteres)

**Problema.** El slug de URL de un proyecto se deriva del **nombre traducido** en
`src/lib/catalog.ts` → `langSlugs()` (línea ~128: `const base = slugify(t(p.name));`). Hay 11 proyectos
con slug >70 caracteres y 4 >120; el máximo es 234:

```
emili-godes-montserrat-godes-antonia-diago-dolores-almuzara-emilia-giro-artur-godes-genaro-lacoste-mercedes-godes-merce-sagarra-eugenia-gurth-dolors-godes-francesc-ferrer-rosa-godes-joan-pujol-artur-godes-josep-maria-godes-ramon-godes
```

Eso genera rutas de ~280 caracteres: malas para compartir/analítica y ya provocan pérdidas al sincronizar
(ver T1). No son un problema de corrección, pero sí de robustez.

**Cambio propuesto.**

1. En `src/lib/catalog.ts`, añadir un helper determinista y usarlo **solo para URLs** (mantener
   `p.slug` como ID interno, porque lo usan `destacadas.json`, `exposicion-1944.json` y el hash):

```ts
/** Máximo de caracteres del slug de URL; si se recorta, se añade un sufijo estable para no colisionar. */
const MAX_URL_SLUG = 70;
function urlSlug(text: string): string {
  const full = slugify(text);
  if (full.length <= MAX_URL_SLUG) return full;
  const cut = full.slice(0, MAX_URL_SLUG - 6).replace(/-[^-]*$/, ''); // corta en frontera de palabra
  let h = 0;
  for (let i = 0; i < full.length; i++) h = (h * 31 + full.charCodeAt(i)) >>> 0;
  return `${cut}-${h.toString(36).slice(0, 5)}`;
}
```

   Y en `langSlugs()`: `const base = urlSlug(t(p.name));` (la resolución de colisiones `-2`, `-3` ya
   existe y se mantiene).

2. **Redirecciones obligatorias** (cambiar un slug cambia la URL pública). Procedimiento seguro,
   independiente de los idiomas:
   - Antes del cambio, con un build limpio, guardar los JSON de datos: copiar
     `dist/data/catalog.*.json` a una carpeta temporal.
   - Aplicar el cambio y volver a construir.
   - Generar `public/_redirects` comparando por el campo **`slug` interno** (estable) entre el JSON
     viejo y el nuevo, usando `uslug`/`url` de cada idioma:

```python
# pseudocódigo: para cada lang, para cada proyecto con el mismo slug interno
#   viejo: /<lang>/.../<uslug_viejo>/   nuevo: /<lang>/.../<uslug_nuevo>/
#   añadir: <viejo>*  <nuevo>  301
```

   - Añadir esas líneas al final de `public/_redirects` (respetando el formato existente y los
     comentarios con `#`).

3. Comprobar que el hash del explorador sigue aceptando el slug antiguo: `explorer.ts` ya busca
   `p.uslug === parts[1] || p.slug === parts[1]`, así que no hace falta tocar nada.

**Aceptación.**
- Ningún slug de URL supera 70–80 caracteres en los 6 idiomas.
- `public/_redirects` contiene una línea 301 por cada URL antigua afectada y por idioma.
- El build no lanza «Dos temáticas con el mismo slug» ni duplica slugs dentro de una temática.
- `sitemap.xml` y `sitemap-images.xml` usan las URLs nuevas.
- Abrir una URL antigua en producción (tras desplegar) devuelve 301 a la nueva.

**Riesgo.** Si no se generan las redirecciones, se rompen enlaces indexados. **No hacer T3 sin redirecciones.**

### T9 · P2 — Endurecimiento

**9a. Formulario sin rate limit.** `functions/api/contact.ts` solo tiene honeypot + Turnstile opcional.
Recomendado: exigir Turnstile en producción (documentar `TURNSTILE_SECRET` como obligatorio en
`docs/DEPLOY.md`) y/o añadir una regla de **Rate Limiting** en Cloudflare (no hacerlo en memoria del
Worker: no es fiable). No implementar un limitador casero con estado global.

**9b. Cabeceras.** `public/_headers` no tiene CSP ni HSTS. Añadir, tras probar:
```
/*
  Strict-Transport-Security: max-age=31536000; includeSubDomains
```
La CSP es delicada (Astro emite scripts inline y GTM inyecta otros): si se añade, debe permitir
`'unsafe-inline'` en `script-src` o usar hashes, y autorizar `googletagmanager.com`,
`google-analytics.com`, `challenges.cloudflare.com` (frame) y `api.resend.com` no hace falta (es
servidor). **Probar en preview antes de publicar**; si algo se rompe, dejar solo HSTS y documentar.

**Aceptación.** El formulario sigue enviando con Turnstile activado; no hay errores de CSP en consola;
`curl -I` muestra la cabecera nueva.

## 4. Orden recomendado de implementación

1. **T1** (entorno) — sin esto no hay build.
2. **T2** (404), **T5** (limpieza) y **T4** (CI) — bajo riesgo, alto retorno.
3. **T6** (accesibilidad) y **T7** (hero) — cambios acotados, fáciles de revisar.
4. **T3** (slugs) — hacerlo aparte, con la captura previa de `catalog.*.json` y las redirecciones.
5. **T9**, **T10**, **T11**, **T13** — endurecimiento y detalles.
6. **T8** y **T12** — refactor de rendimiento; dejar para el final y medir antes/después.

**Definición de «hecho»:** `npm run check` y `npm run build` en verde, cifras de la documentación
actualizadas, sin enlaces internos roos, sin artefactos `*Conflict*`, y un commit por bloque con mensaje
descriptivo (el proyecto commitea y hace push a `main` al terminar cada bloque).
